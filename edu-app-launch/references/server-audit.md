# 서버·계정 점검 (B형)

서버 저장이나 로그인이 있는 앱에서 코드와 설정을 실제로 읽고 확인한다. 확인하지 못한 것은 "괜찮다"가 아니라 "확인 못 함"으로 보고한다.

## 1. 데이터 접근 규칙 (가장 급함)

화면을 숨겨도 데이터 주소는 열려 있을 수 있다. 학생 정보를 지키는 것은 화면이 아니라 이 규칙이다.

| 쓰는 것 | 확인할 것 |
|---|---|
| Supabase | 학생 정보가 든 모든 테이블에 RLS가 켜져 있다. 정책이 `auth.uid()`나 학급처럼 실제 조건으로 좁혀져 있고 `using (true)`처럼 전부 허용하는 정책이 없다. 학생 사진이 든 Storage 버킷이 public이 아니다. 대시보드의 Security Advisor(또는 Supabase MCP의 보안 진단)를 함께 본다. |
| Firebase | `firestore.rules`, `storage.rules`에 `allow read, write: if true`나 날짜로만 막는 테스트 모드 규칙이 없다. `request.auth.uid` 기준으로 좁혀져 있다. |
| 앱스스크립트 | 웹앱을 "모든 사용자"로 배포하면 주소를 아는 누구나 `doGet`·`doPost`를 부를 수 있다. 시트 전체를 돌려주지 않고 화면에 필요한 값만 돌려주는지, 받은 값을 검사하는지 본다. |

## 2. 비밀 키

| 공개해도 되는 키 | 클라이언트에 두면 안 되는 키 |
|---|---|
| Supabase anon(publishable) 키, Firebase 웹 설정의 `apiKey`. 단, 1번 규칙이 지켜 줄 때만 안전하다 | Supabase service_role(secret) 키, Firebase 서비스 계정 키(`private_key`), AI·번역·문자 발송 API 키 |

- 찾기: `grep -rnE "service_role|sb_secret_|private_key|generativelanguage|api\.openai|api\.anthropic" --exclude-dir=node_modules .` 빌드하는 앱은 빌드 결과 폴더(`dist` 등)도 찾는다. 빌드 결과에 들어간 값은 모두 공개된다.
- `.env` 파일이 저장소에 올라가 있지 않은지 본다(`git ls-files | grep -i env`).
- 고치기: 키를 서버리스 함수(Vercel Functions, Supabase Edge Functions)로 옮기고 클라이언트는 그 함수를 부른다.
- 이미 공개 저장소나 배포본에 올라간 키는 지워도 기록에 남는다. 재발급하라고 알린다(사람이 할 일).

## 3. 교사·관리자 화면

- 로그아웃 상태로 `/admin`, `/teacher` 같은 주소에 바로 들어가지는지 본다. 화면 가드(`ProtectedRoute` 등)는 편의일 뿐이고, 데이터는 1번 규칙이 막아야 한다.
- 교사 권한을 `localStorage` 값이나 숨긴 버튼처럼 클라이언트 쪽 표시로 판단하지 않는다. 권한은 DB(역할 테이블 등)나 서버에서 확인한다.
- 학급 코드·짧은 비밀번호로 직접 만든 로그인은 몇 번이고 넣어 볼 수 있다. 시도 횟수 제한이 있거나 코드가 충분히 긴지 본다.

## 4. 점수·포인트·결제 값

- 브라우저에서는 누구나 값을 바꿔 보낼 수 있다. 클라이언트가 보낸 가격·포인트·점수를 그대로 저장하거나 결제에 쓰지 않는다.
- 결제는 서버에서 상품 ID로 DB를 다시 조회해 금액을 계산하고, 다르면 거부한다.
- 순위·보상이 걸린 점수는 서버에서 검사하거나, 조작돼도 괜찮은 값인지 사용자와 정한다.

## 5. 오류 메시지와 로그

- 배포본 화면에 스택 트레이스, 테이블 이름, 파일 경로, DB 오류 원문이 보이지 않는다. 사용자에게는 쉬운 한국어 안내만 보이고 자세한 내용은 서버 로그에만 남긴다.
- 서버 로그(서버리스 함수의 `console.log` 등)에 비밀번호·토큰·학생 정보를 통째로 찍지 않는다.
